# 认证与访问控制专项审查

在**已授权**前提下，对目标的认证与授权面做系统性核查。核心问题只有一个：**每个敏感操作，服务端有没有独立验证「当前请求者是谁、有没有权限」**——而不是前端藏了入口、接口没暴露、ID 不可枚举这类「隐式防线」。

## 与平台工作流的分工

- 铺面：先拿到**角色矩阵**（有哪些角色、各能做什么）和**对象清单**（有归属的敏感对象：订单/文档/用户资料）——没有矩阵的越权测试是瞎撞。
- 追链/验证中的一切中间结论 → `record_fact`；**确证的越权 → `report_finding`**（附双账号 PoC 与 traffic_refs）。

## 五个核查面

### 1. 垂直越权（提权）

低权账号直接请求**高权端点**：把管理端路径/参数（`/admin/*`、`role=1`、`is_admin=true`）逐个用普通会话重放。重点：
- 前端藏起来的管理接口（JS 里翻到的路由）——**前端藏 = 服务端大概率没拦**，逐一验证；
- 角色字段可否自改（注册/资料更新接口的 mass-assignment）；
- JWT 的 header/payload 可改字段（alg=none、kid 注入、claims 复制）——改了服务端认不认。

### 2. 水平越权（IDOR）

对象级授权是重灾区：账号 A 的会话 + 账号 B 的对象 ID。重点：
- ID 可枚举性只是**放大因子**，不可枚举（UUID）不等于没洞——直接拿两个号测；
- **非 ID 引用面**：邮箱/手机号/用户名做参数的查询与修改；
- 批量接口（导出/列表/搜索）里的归属过滤——单条有过滤、批量没有是常见漏法；
- **越界不等于可读**：能「看到别人订单号」和「能拉到别人订单内容」是两个等级，evidence 按实际拉到的数据写。

### 3. 会话管理

- 登录后 token 有没有换发（旧 token 还有效吗）；登出后 token 还能用吗；
- 修改密码/邮箱后其它会话是否被踢（不踢 = 已泄露会话永久有效）；
- 会话固定：登录前后 token 是否同一枚；
- Cookie 属性（Secure/HttpOnly/SameSite）与 token 有效期——记 fact，单独不构成 finding（提示词 0 元清单）。

### 4. 认证流程本身

- 验证码/OTP 的可绕过形态：响应包置空、爆破限速缺失（单独不算 finding）、**验证码先发后验**（流程顺序漏洞）；
- 密码重置链：token 可预测/可复用/不过期、host header 投毒改变重置链接；
- 多因素可跳过：改 response 的 verify 结果、先 finalize 后 verify。

### 5. 租户隔离（多租户目标）

跨租户数据访问用「租户 A 会话 + 租户 B 对象 ID」对测；子域名/路径分租的场景核查路由解析能否串租户；共享资源（文件/报表）的租户归属校验。

## 纪律

- **双账号是标配**：越权结论必须「A 号会话 + B 号对象」双坐实，单侧推测不报。
- 只做**验证性读取/最小影响写**：证明越权即可，不批量拉数据、不改动他人对象（破坏性验证按平台红线走审批）。
- 越权到敏感数据后停止深入，落 finding；继续横向扩面属于范围决策，交规划者。
