# 污点追踪专项审计（Web 语境）

在**已授权**前提下，把「不可信输入 → 危险汇」的完整链路追出来：不是扫一遍参数面，而是对每一个候选链给出**两端都坐实**的证据（入口可注入 + 汇点可达）。

## 与平台工作流的分工

- 本 skill 是**深钻手册**：候选面已铺开后的专项。铺面用常规侦察（资产图/端点枚举）。
- 追链过程中的一切中间结论 → `record_fact`（标 observed/inferred）；**只有两端坐实的链才走 `report_finding`**（含 PoC 与 traffic_refs 绑定）。
- 证据流量用 `traffic_search`/`traffic_get` 回看，不要重复发包。

## 四步循环

### 1. 定源（Source）

候选不可信输入按可信度排序：**URL 参数 > JSON body 字段 > Header（Referer/XFF 等）> 文件名/上传内容 > 二级源**（存库后回显的值——存储型链的关键，别只看当次请求）。每个源记：参数名、所在端点、到达方式（GET/POST/上传）。

### 2. 定汇（Sink）

按 vulnclass 对照典型汇：

| 类别 | 典型汇 |
|---|---|
| SQLi | 拼接进 SQL 的字符串（报错形态/ORDER BY 注入面） |
| SSTI/模板 | 渲染引擎的模板变量（邮件模板、PDF 导出、告警文案） |
| SSRF | 服务端发起请求的 URL 参数（webhook/预览/导入） |
| 命令注入 | system/exec/popen 的拼接段（文件名、转码参数） |
| 路径穿越 | 文件读写路径参数（下载/导出/解压） |
| 反序列化 | session/缓存/上传文件的还原点 |

### 3. 追链（Path）

- **正向追**：从源跟框架的数据流（路由→controller→service→ORM/驱动）；框架层净化点（escape/parametrize/白名单）逐个核对——**净化了什么字符集、没净化什么**才是链是否成立的关键。
- **反向追**：从汇点搜调用者（谁把用户数据传进来了）。正向走不通时反向常有意外的短链。
- 二级链（stored）：源注入 → 存库 → 另一个上下文取出使用——两段都要各自验证，别拿「存进去了」当「触发了」。

### 4. 坐实（Prove）

每条候选链的自检（对抗式）：用**与首次不同的路径或独立命令**再触发一次；报 `report_finding` 时 evidence 必须含两端证据（入口 payload + 汇点响应/效果）。链断在中间（源可注入但汇不可达）→ `record_fact` 标 inferred，一句话写清断在哪。

## 纪律

- 每条链独立验证，禁止用「同类参数别处注入成功」推断本链成立。
- 净化点分析要有证据（实际发绕过 payload 看 response），「代码看起来净化了」不算数。
- 只在授权范围内追链；汇点副作用大的（删除/RCE 类）先降级验证（时延盲注/布尔盲注）再升级。
